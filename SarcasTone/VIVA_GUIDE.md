# SarcasTone — Viva Reference Guide

Everything used in this project to compute a "sarcasm probability", organized for
an oral exam: tools/libraries, every function that participates in the pipeline,
the exact step-by-step math/logic from raw input to final probability, the
evaluation methodology, the numbers, and likely questions with ready answers.

---

## 1. One-paragraph summary (lead with this)

SarcasTone is a **multimodal sarcasm detector** built on the **MUStARD** dataset
(690 labelled TV-sitcom utterances, Castro et al., ACL 2019). It has three
models — **text-only** (TF-IDF + Logistic Regression), **speech-only**
(prosodic/acoustic features + Random Forest), and **multimodal** (late fusion
of the two via a small meta-classifier) — served by a FastAPI backend and
visualized by a React/TypeScript dashboard. Every number the UI shows is read
from `results/metrics.json`, generated by the training script — nothing is
hardcoded. Evaluation is **speaker-independent 5-fold GroupKFold** cross-
validation (grouped by `speaker`) specifically to prevent vocabulary/speaker
leakage between train and test folds.

## 4. Function-by-function reference

### `backend/app/ml/data.py` — dataset loading & text preprocessing

| Function | Signature | What it does |
|---|---|---|
| `clean_text` | `(t: str) -> str` | Lowercases, strips everything except `a-z0-9'!?.,` and spaces, collapses whitespace. Basic text normalization before vectorization. |
| `sentiment_shift` | `(clean: str) -> dict` | **Key engineered feature.** Splits the sentence on clause boundaries (`,`, `;`, `but`, `yet`, `except`, `although`, `though`, `however`) — or in half if no such boundary exists — runs **VADER** on each half, and returns `sent_shift` (absolute difference in compound sentiment between the two halves), `sent_min`, `sent_max`. Captures the classic sarcasm pattern "positive setup → negative payoff" (e.g. "wonderful day, already had an accident") that a bag-of-words model can't see on its own. |
| `load_dataframe` | `() -> pd.DataFrame` | Reads `sarcasm_data.json`, builds one row per utterance (`id`, `text`, `speaker`, `show`, `label`, `n_context`, `audio_path` if the WAV exists), applies `clean_text` and `sentiment_shift` to every row, adds `has_audio`. This is the single source DataFrame everything else is built from. |

### `backend/app/ml/features.py` — acoustic/prosody feature extraction (Librosa)

| Function | What it computes |
|---|---|
| `_highpass(y, sr, cutoff=60)` | 4th-order Butterworth high-pass filter (SciPy `butter`+`sosfiltfilt`) removing DC offset / rumble below 60 Hz, so live-mic recordings aren't artificially different from studio audio on that axis. |
| `load_audio(path, sr=16000)` | Loads audio mono at 16kHz, trims leading/trailing silence (`librosa.effects.trim`, `top_db=30`), applies the high-pass filter, then **RMS-normalizes loudness** to a fixed target (`TARGET_RMS=0.1`) and clamps any clipping peak. This exact function is called identically at **training time and serving time**, which is what makes live recordings comparable to the training distribution. |
| `contours(y, sr)` | Computes the **pitch (F0) contour** via `librosa.pyin` (probabilistic YIN, range 70–400 Hz) and the **RMS energy contour** (`librosa.feature.rms`), aligned on a shared time axis. Unvoiced frames get F0 = NaN. |
| `pause_stats(rms, hop, sr)` | Thresholds the RMS energy at 10% of its max to find low-energy runs; a run becomes a "pause" if it's ≥ 0.15 seconds. Returns the list of pause durations. |
| `speaking_rate(y, sr)` | **Approximate syllable rate** — picks peaks in the RMS envelope (`librosa.util.peak_pick`) as a proxy for syllable nuclei, divides peak count by duration. Explicitly an approximation, not real ASR/forced alignment. |
| `feature_vector(y, sr)` | Builds the full **~45-dimensional prosody feature vector** fed to the speech model: duration; F0 mean/std/min/max/range; voiced ratio; RMS mean/std/max; zero-crossing-rate mean/std; spectral centroid mean/std; spectral rolloff mean; spectral bandwidth mean; speaking rate; pause count/total/mean/ratio; and 13 **MFCCs** (mean+std each = 26 values). |
| `FEATURE_NAMES` | Module-level constant: the exact ordered list of feature-vector keys, computed once from a probe signal — this fixes column order so the model always sees features in the same order it was trained on. |

### `backend/app/ml/train.py` — training & evaluation

| Function | What it does |
|---|---|
| `load_external_text()` | Loads the ~28.6k News Headlines rows, cleans text, computes `sentiment_shift` for each — produces the extra training-only data used to widen the text model's vocabulary. |
| `_one(i, path)` / `build_audio_features(df)` | Extracts the prosody feature vector for every audio clip, **in parallel** (`joblib.Parallel`, all CPU cores), with a CSV cache (`experiments/audio_features.csv`) so re-runs don't recompute unchanged clips. |
| `text_pipe()` | Builds the **text-only sklearn Pipeline**: a `ColumnTransformer` combining (a) `TfidfVectorizer(ngram_range=(1,2), min_df=2, sublinear_tf=True)` on the cleaned text and (b) `StandardScaler` on the 3 sentiment-shift columns, feeding a `LogisticRegression(C=1.0, max_iter=2000)`. |
| `speech_pipe()` | Builds the **speech-only Pipeline**: `StandardScaler` → `RandomForestClassifier(n_estimators=300, min_samples_leaf=2, n_jobs=-1)`. |
| `evaluate(name, make, X, y, groups, inp, extra_X, extra_y)` | **Core CV loop.** Runs 5-fold `GroupKFold` (grouped by `speaker`, so no speaker's utterances appear in both train and test of the same fold). Optionally appends extra (external) training rows to each fold's *training* split only — the held-out test fold is always pure MUStARD. Collects out-of-fold predicted probabilities, computes accuracy/precision/recall/F1/ROC-AUC/confusion matrix/ROC curve, and times training/inference. Also fits one final model on *all* data for deployment. |
| `external_holdout_eval(make, ext_X, ext_y, muse_X, muse_y, holdout_frac=0.15)` | A separate, large-N (~4,293 examples) sanity check: holds out 15% of the headline dataset, trains on MUStARD + the remaining 85% of headlines, evaluates purely on the held-out headlines. This is the number that actually reflects real-world ("does it work on ordinary English") performance, since MUStARD's own speaker-independent metric is near chance. |
| `evaluate_fusion(text_make, speech_make, text_X, speech_X, y, g, ext_X, ext_y)` | CV loop for the **multimodal (late-fusion) model**. Inside each GroupKFold split: trains a fresh text model and fresh speech model on the fold's training rows, gets each one's predicted probability on both train and test rows, and fits a 2-input `LogisticRegression` **meta-model** on `[p_text, p_speech]` → true label. Wraps the final fitted text model, speech model, and meta-model into a `StackedFusion` object. |
| `main()` | Orchestrates everything: loads the dataframe, runs `evaluate()` for text (with external headlines) and prints/saves metrics, extracts audio features and runs `evaluate()` for speech if ≥90% of rows have audio, runs `evaluate_fusion()` for multimodal, saves all three `.joblib` models and the single `results/metrics.json`. |

### `backend/app/ml/fusion.py` — the multimodal model object

| Class | What it does |
|---|---|
| `StackedFusion` | A plain Python object (not a sklearn `Pipeline`) holding references to the fitted `text_model`, `speech_model`, and `meta` (logistic regression). `predict_proba(X)` runs the text model on the text+sentiment columns, the speech model on the prosody feature columns, stacks the two probability columns, and runs the meta-model on that 2-column input to get the final `[P(non-sarcastic), P(sarcastic)]`. This is **late fusion / stacking**: each branch keeps its own full training data and architecture; only the lightweight meta-model is fit on the 690 rows where both audio and text exist — avoiding the problem of being stuck with only 690 rows for a single joint model (headlines have no audio). |

### `backend/app/services/ml_service.py` — inference-time service layer

This is **where a sarcasm probability actually gets produced at request time.**

| Method | What it does |
|---|---|
| `MlService.__init__` | Loads whichever of `text_model.joblib` / `speech_model.joblib` / `fusion_model.joblib` exist on disk, and loads `results/metrics.json` for reporting CV accuracy alongside predictions. Models that aren't trained are simply absent — no fabricated predictions. |
| `cv_acc(key)` | Looks up a model's officially reported cross-validated accuracy from the loaded metrics, to attach to every prediction response (so the UI can show "this model is X% accurate" next to its output). |
| `_pred(p)` *(static)* | Converts a raw `[P(0), P(1)]` probability pair into the response shape: `label` (`"Sarcastic"` if `p[1] >= 0.5` else `"Non-Sarcastic"`), `confidence` (the larger of the two probabilities), and the full `probabilities` dict. **This is the literal "sarcasm probability" the whole project produces** — `p[1]`, the model's predicted probability of the positive (sarcastic) class. |
| `sentiment(text)` *(static)* | Runs VADER, buckets the compound score into positive/neutral/negative for display. |
| `_top_terms(clean, shift, k=6)` | **Explainability.** Pulls the fitted `TfidfVectorizer` and `LogisticRegression` out of the text pipeline, re-transforms the input text to get which TF-IDF features are non-zero, multiplies each feature's TF-IDF value by its logistic-regression coefficient (contribution to the log-odds), does the same for the 3 scaled sentiment-shift features, and returns the top-k terms by `abs(contribution)` — i.e. "which words pushed this prediction toward Sarcastic/Non-Sarcastic." |
| `text(text)` | **Text-only inference pipeline**: clean the input → compute `sentiment_shift` → build a 1-row DataFrame → `predict_proba` through the loaded text pipeline → format via `_pred` → compute top contributing terms → compute VADER sentiment → build a human-readable explanation string (including the near-chance-accuracy caveat) → attach the model's CV accuracy and timing. |
| `_audio_scaler(key)` | Reaches into the speech (or fusion's internal speech) pipeline to get the fitted `StandardScaler`, needed for domain-shift detection. |
| `_typicality(fv, key)` | **Domain-shift / out-of-distribution detector.** Z-scores the live feature vector against the *training* `StandardScaler`'s mean/std (`z = |x - mean| / std`), and flags `out_of_distribution=True` if the mean z-score > 1.5 or more than 15% of features have `z > 3`. This is why a recording that sounds nothing like the TV-sitcom training data gets an explicit warning instead of a confidently-wrong prediction. |
| `_to_wav(path)` *(static)* | Shells out to `ffmpeg` to convert any uploaded audio format to mono 16kHz WAV, if ffmpeg is on PATH. |
| `analyze_audio(raw, suffix)` | Writes the uploaded bytes to a temp file, converts to WAV, runs `load_audio` (trim+highpass+RMS-normalize), rejects audio shorter than 0.3s after trimming, computes pitch/energy contours, MFCCs, a downsampled waveform for plotting, and pause segments — returns both the full visualization payload (`analysis`) and the raw numeric `feature_vector` (`fv`) used for prediction. |
| `audio(raw, suffix, text=None, mode="audio")` | Top-level entry for `/api/analyze/audio` and `/api/analyze/multimodal`. Calls `analyze_audio`, then: for **speech-only**, builds `X` from the prosody feature vector and runs it through the speech model; for **multimodal**, additionally cleans+sentiment-shifts the user's typed text and builds a combined row that `StackedFusion` internally slices into its text and speech inputs. Attaches `_pred`, CV accuracy, the `_typicality` domain-shift check, and an explanation string. If the relevant model isn't trained, returns the acoustic measurements with `model_available=False` and no fabricated prediction. |

## 5. Exactly how a "sarcasm probability" is produced — step by step

### A. Text-only (`/api/analyze/text`)
1. User's raw text → `clean_text()` (lowercase, strip punctuation, collapse whitespace).
2. `sentiment_shift()` splits the cleaned text into two clauses (on conjunctions/punctuation, or in
   half if none found), runs VADER on each half, outputs `sent_shift` / `sent_min` / `sent_max`.
3. Builds a 1-row `pandas.DataFrame` with columns `clean`, `sent_shift`, `sent_min`, `sent_max`.
4. Feeds it through the loaded `text_model.joblib` pipeline:
   - `ColumnTransformer` → TF-IDF vectorizes `clean` (1–2 grams) **and** `StandardScaler`s the 3
     sentiment columns, concatenated into one feature vector.
   - `LogisticRegression.predict_proba()` → sigmoid of the weighted sum of all those features →
     `[P(Non-Sarcastic), P(Sarcastic)]`.
5. `P(Sarcastic)` ≥ 0.5 → label `"Sarcastic"`; `confidence` = the larger of the two probabilities.
6. `_top_terms()` recomputes which TF-IDF/sentiment features were non-zero and multiplies by the
   logistic-regression coefficients to show which words drove the decision.

### B. Speech-only (`/api/analyze/audio`)
1. Uploaded audio bytes → temp file → `ffmpeg` converts to mono 16kHz WAV if needed.
2. `load_audio()`: trim silence → high-pass filter (remove rumble) → RMS-normalize loudness.
3. `feature_vector()`: pitch contour (`pyin`), RMS energy, 13 MFCCs, zero-crossing rate, spectral
   centroid/rolloff/bandwidth, speaking rate (peak-picking), pause statistics → ~45 numeric features.
4. Build a 1-row DataFrame with exactly the `FEATURE_NAMES` columns, in the fixed order.
5. `StandardScaler` → `RandomForestClassifier.predict_proba()` (majority vote across 300 trees, each
   trained on a bootstrap sample with random feature subsets) → `[P(Non-Sarcastic), P(Sarcastic)]`.
6. `_typicality()` z-scores this feature vector against the training distribution's mean/std; if the
   recording is statistically unlike the 690 TV-sitcom training clips, a domain-shift warning is
   attached so the probability isn't presented as more trustworthy than it is.

### C. Multimodal (`/api/analyze/multimodal`)
1. Runs **both** the text preprocessing (A, steps 1–2) and the audio feature extraction (B, steps
   1–3) on the user's typed text and recorded/uploaded audio respectively.
2. `StackedFusion.predict_proba()`:
   - Slices out the text+sentiment columns → runs the **already-trained headline-augmented text
     model** → `p_text` = P(Sarcastic) from text alone.
   - Slices out the prosody feature columns → runs the **already-trained speech Random Forest** →
     `p_speech` = P(Sarcastic) from audio alone.
   - Stacks `[p_text, p_speech]` as a 2-feature input to a small fitted `LogisticRegression`
     **meta-model**, which outputs the final combined `[P(Non-Sarcastic), P(Sarcastic)]`.
3. Same domain-shift check as (B) is run on the speech side, since the prosody branch is the one
   with the acoustic-mismatch risk.

**The one-line answer if asked "what is the sarcasm probability":** it is literally
`model.predict_proba(X)[0][1]` — the second column of whichever classifier's probability output,
i.e. the model's estimated probability that the positive class ("Sarcastic") is correct, thresholded
at 0.5 to produce the displayed label.

## 6. Models, why they were chosen, and hyperparameters

| Model | Algorithm | Hyperparameters | Why this choice |
|---|---|---|---|
| Text | **Logistic Regression** on **TF-IDF** (word 1–2 grams) + 3 sentiment-shift features | `C=0.3`, `class_weight="balanced"`, `max_iter=2000`, `ngram_range=(1,2)`, `min_df=2`, `sublinear_tf=True` | Linear model on sparse TF-IDF is a strong, fast, interpretable baseline for short-text classification; coefficients give direct word-level explainability (`_top_terms`). Char n-grams and stopword removal were tried and measured *worse* on the large holdout (see §7) — kept the simpler model. `C` was lowered from `1.0` and `class_weight="balanced"` added after diagnosing function-word overfitting on conversational input (see §11) — this is the current, retrained configuration. |
| Speech | **Random Forest** (300 trees) on standardized prosody features | `n_estimators=300`, `min_samples_leaf=2`, `n_jobs=-1` | Tree ensembles handle the mixed scales/non-linear interactions of ~45 heterogeneous acoustic features (Hz, dB-like ratios, counts, ratios) without needing careful feature engineering of interactions, and resist overfitting on a small (690-row) dataset better than a deep model would. |
| Multimodal | **Late fusion / stacking**: reuse both trained models, add a 2-input **Logistic Regression** meta-model on `[p_text, p_speech]` | `max_iter=1000` for the meta-model | A single joint model on raw concatenated features would be limited to the 690 rows that have *both* text and audio (headlines have no audio), discarding the vocabulary benefit of the text model's extra training data. Stacking lets each branch use its best available data/architecture; only the lightweight 2-parameter-ish meta-model needs to be fit on the 690 paired rows, so overfitting risk there is minimal. |

## 7. Evaluation methodology — be ready to explain every term

- **GroupKFold(n_splits=5), grouped by `speaker`**: ensures no speaker's utterances appear in both
  the training and test portion of the same fold. Plain random/stratified k-fold lets the model
  partly memorize *who* says *what* (vocabulary tied to a specific character), which **inflates**
  accuracy (demonstrated in `experiments/exploratory_text_variants.py`: random split ≈ 59% vs.
  speaker-independent ≈ 48.8% for the same word-TF-IDF model) — a dishonest, overoptimistic number.
- **Out-of-fold (OOF) predictions**: for each fold, the model trains only on the other 4 folds and
  predicts on the held-out fold; stacking all 5 held-out predictions together gives one accuracy/F1/
  ROC-AUC number computed over the *entire* dataset without any row being evaluated by a model that
  saw it during training.
- **Fit-inside-the-fold discipline**: `TfidfVectorizer`/`StandardScaler` are refit inside each
  training fold (never on the full dataset before splitting) — otherwise the vectorizer's vocabulary
  or the scaler's mean/std would leak information from the test fold into training.
- **External-only training augmentation**: the ~28.6k headline rows are added to each fold's
  *training* split only; the evaluation/test fold is always pure, untouched MUStARD — so the reported
  speaker-independent metric cannot be inflated by the external data, even though the *deployed*
  model benefits from it.
- **Metrics reported per model**: `accuracy`, `precision`, `recall`, `f1` (all at the 0.5 probability
  threshold), `roc_auc` (threshold-independent, computed from the OOF probabilities), the full
  `confusion_matrix`, a downsampled `roc_curve` (fpr/tpr arrays), plus wall-clock `train_time` and
  per-sample `inference_time_ms` — all genuinely measured during training, not estimated.
- **`external_holdout_eval`**: a *second*, separate evaluation — 15% of the headline dataset held
  out, trained on MUStARD + the remaining 85% of headlines, tested purely on the held-out headlines.
  This answers a different question than the MUStARD CV metric ("does the *deployed* model work on
  ordinary English?") with enough examples (4,292) to trust a small accuracy difference between
  pipeline variants, unlike an 8-sentence manual spot-check.

**Why text-only's official number looks like "near chance" (0.49 accuracy on a balanced binary

holdout number is the one that reflects that model's actual usefulness — just be ready to explain
**why there are two different numbers for the same model** (see §9, Q&A).

acoustic domain (studio-mixed TV audio, a handful of actors) — a small, narrow dataset for a 45-
dimensional feature space. 62% vs. a 50% chance baseline on a binary task is a real, modest signal,
not noise, but it's not near-perfect, and it carries a known generalization gap to live-mic audio
(see §9).

## 9. Likely viva questions, with ready answers

**Q: What exactly is "sarcasm probability" — where does the number come from?**
A: It's `predict_proba()`'s second column from whichever scikit-learn classifier is active — a
calibrated-by-training-data estimate of P(class = Sarcastic | features), thresholded at 0.5 to pick
the displayed label. See §5 for the exact feature pipeline per mode.

**Q: Why GroupKFold by speaker instead of a normal train/test split?**
A: To prevent the model from learning "this specific character talks like X" instead of general
sarcasm cues. Demonstrated empirically in `exploratory_text_variants.py`: the same model scores ~10
points higher accuracy under a random split purely from speaker leakage — that number would be
dishonest.

**Q: The text model's MUStARD accuracy (49%) is basically chance on a binary task — isn't that a
failure?**
A: It's a known, documented limitation of training on only 690 lines from 4 shows, not a bug (both
label mapping and the probability display were independently verified correct). It's why the
deployed model is additionally trained on ~28.6k generic headlines, and why we report a *second*,
larger-sample metric (`text_only_generic_english_holdout`, 84.3% accuracy / 0.924 ROC-AUC) that's the
one that actually reflects real-world usefulness — the MUStARD number stays as the honest,
uncontaminated speaker-independent score for this specific narrow dataset/protocol.

**Q: Why is multimodal not much better than speech-only?**
A: Multimodal is a *late fusion* (stacking) of the text and speech models via a small logistic-
regression meta-model learned on only the 690 rows where both modalities exist — not a single joint
model trained on concatenated raw features (that would be capped at 690 rows too, since headlines
have no audio, and would re-introduce the text model's narrow-vocabulary problem). The meta-model
learns to weight each branch's probability; on this dataset the audio signal already carries most of
the separable information, so the fused number tracks speech-only closely rather than strictly
exceeding it. It did measurably improve versus the old single-joint-model architecture (59.1% → 62.0%
accuracy on the official metric, and 70–85% → 92–97% confidence on in-distribution test clips).

**Q: How do you know predictions on live microphone audio are trustworthy?**
A: We don't claim they always are. `MlService._typicality()` z-scores the live feature vector against
the training `StandardScaler`'s mean/std; if the recording's acoustic profile (pitch/energy/spectral
balance) is far from the 690 TV-sitcom clips the model trained on, `domain_shift.out_of_distribution`
is flagged and the UI shows an explicit warning banner instead of presenting a confident number.
Mitigations (RMS loudness normalization + high-pass filtering identically at train/serve time;
browser-side `autoGainControl`/`noiseSuppression`) measurably narrowed this gap but didn't eliminate
it — there's no code fix for "690 single-domain examples don't cover every voice/environment," that
needs more diverse training data.

**Q: Why TF-IDF + Logistic Regression instead of a transformer/BERT?**
A: Dataset size (690 labelled rows, or ~29k with headlines) is small for fine-tuning a transformer
without heavy regularization/risk of overfitting; a linear model on TF-IDF is fast, fully
interpretable (direct per-word coefficient contributions via `_top_terms`), and establishes a
reproducible, auditable baseline appropriate for a course-scale project with a "no hardcoded numbers"
requirement.

**Q: Why Random Forest for audio instead of a CNN on spectrograms?**
A: 690 examples is far too few to train a convolutional model on raw spectrograms without severe
overfitting. Hand-engineered prosodic summary statistics (pitch, energy, MFCCs, spectral shape, pause
timing, rate) compress each clip to ~45 numbers, which a tree ensemble can model well with a small
sample size, and it's directly interpretable (feature importances, z-score domain-shift check)
without needing a GPU or thousands of labelled clips.

**Q: What does "fit inside each fold" mean and why does it matter?**
A: The `TfidfVectorizer` and `StandardScaler` are refit from scratch on each fold's training split
only, inside the `evaluate()` CV loop — never fit once on the whole dataset before splitting. If they
were fit globally first, the vectorizer's vocabulary or the scaler's mean/std would have "seen" the
test fold's data, leaking information and inflating the reported metric; this is a common, subtle
mistake in ML evaluation that this project explicitly avoids.

**Q: What's the sentiment_shift feature and why engineer it explicitly instead of trusting TF-IDF?**
A: A bag-of-words model scores words independently and can't represent *relational* structure like
"positive clause, then negative clause" — the single strongest textbook sarcasm cue. `sentiment_shift`
computes VADER compound sentiment on each half of the sentence and feeds the absolute difference
(plus min/max) as explicit numeric features, giving the classifier a direct signal for that pattern
instead of hoping scattered word weights happen to capture it.

**Q: Is this feature actually helping?**
A: Measured as statistically a wash on the large holdout (84.2% vs 84.3% accuracy with/without) — kept
anyway because it's not harmful, directly targets a known failure pattern, and adds a transparent,
labeled term to the explanation output. This is a good example of evaluating a feature change on a
large held-out number rather than a handful of manual examples (stopword removal, by contrast, looked
good on one example but measured clearly worse on the large holdout and was reverted).

**Q: Where are the model files and why are two of the three not in git?**
A: `backend/app/models/*.joblib`. Only `text_model.joblib` is committed — `speech_model.joblib` and
`fusion_model.joblib` need the MUStARD audio clips (`dataset/audio/*.wav`, ~111MB), which are
gitignored since redistributing the raw dataset isn't appropriate; anyone who clones the repo gets
text-only until they run `scripts/setup_audio.py`, which downloads the clips, extracts WAVs with
ffmpeg, and retrains all three models.

**Q: What happens if someone asks for a prediction before the speech/fusion models exist?**
A: The backend never fabricates a prediction. `MlService` only loads `.joblib` files that exist on
disk; `/api/health`'s `audio_models_trained` flag and `model_available` in the audio response reflect
this honestly, and the UI renders an explicit "model not trained yet, run setup_audio.py" state instead
of guessing.

**Q: How is the frontend kept consistent with "no hardcoded metrics"?**
A: Every number shown anywhere in the UI is fetched live from `/api/models/metrics` (a direct read of
`results/metrics.json`), `/api/models/exploratory`, or a live `/api/analyze/*`/`/api/dataset/*` call —
there is no metric literal written into any `.tsx` file. If a model/metric changes, it flows
`train.py` → `metrics.json` → `MlService`/`main.py` → `api.ts` → the page, by design.

## 10. Known, honestly-stated limitations (good to mention proactively in a viva)

1. Text-only's **official** MUStARD metric is near chance (49% accuracy) under the honest speaker-
   independent protocol — a real generalization limitation of a 690-line, 4-show dataset, mitigated
   but not solved by headline augmentation (which targets generic English, not sitcom dialogue style).
2. Speech/multimodal models have a documented **domain-shift gap** to live microphone audio (trained
   on studio-mixed TV audio only); mitigated via loudness normalization and an explicit out-of-
   distribution warning, not eliminated.
3. `speaking_rate()` is an RMS-envelope-peak **approximation** of syllable rate, not true ASR/forced
   alignment — stated explicitly in the code's own docstring.
4. The "generic-English holdout" number (84.3%) still measures headline-style written English
   specifically, not spoken conversation — shouldn't be presented as "84% on anything typed."
5. Multimodal is late fusion of two independently-trained branches, not a jointly-learned
   cross-modal representation — a deliberate, documented tradeoff to keep the text branch's full
   training data rather than capping everything at 690 paired rows.

## 11. Case study: diagnosing "most predictions on my own text/voice are wrong"

A natural viva question is "you report 62-84% accuracy, so why does it feel wrong most of the time
when I type my own sentence or use my own voice?" Here's the diagnosis actually performed on this
project, and what it found — a good worked example of debugging an ML system rather than just citing
a number.

**Text — root cause found: function-word overfitting to the headline register.**
`MlService._top_terms()` was used to inspect *why* the model got specific conversational sentences
wrong (not headlines — ordinary typed sentences like "He finished his homework before dinner").
The logistic-regression coefficients it surfaced showed function words — "the" (weight ≈ -1.5), "is"
(≈ -1.4), "my" (≈ -0.9), "he"/"his" — dominating the decision, with magnitudes several times larger
than genuine content words ("surprise", "deadline", "genius") and dwarfing the purpose-built
`sentiment_shift` feature (weight ≈ 0.05). **Diagnosis**: the model had learned register-specific
quirks of the News Headlines training corpus (how headlines use articles/pronouns) rather than
sarcasm itself — and this was invisible to the project's own `text_only_generic_english_holdout`
metric, because that holdout is drawn from the *same* headline register as training, so it can't
detect — and can even reward — overfitting to that register.

**Fix applied and measured**: built a 40-sentence hand-labeled conversational probe set (ordinary
typed sentences, half sarcastic/half not, never used in training), then grid-searched the
`LogisticRegression`'s `C` (inverse regularization strength) and `class_weight`. Landed on
`C=0.3, class_weight="balanced"` (previously `C=1.0`, no class_weight):

| Metric | Before | After |
|---|---|---|
| Conversational probe accuracy (40 sentences) | 60.0% | 67.5% |
| Conversational probe ROC-AUC | 0.647 | 0.655-0.665 |
| Headline holdout accuracy (4,292 examples) | 84.3% | 82.3% |
| Official MUStARD speaker-independent accuracy | 49.0% | 47.4% (no material change; already near chance) |

A real, measured improvement on ordinary text, at a small, deliberate cost on the headline-style
metric. **Re-tried stopword removal again at the same time** (the project had previously tried and
reverted it, see §7/CLAUDE.md) — still worse on *both* metrics even combined with the new
regularization, confirming that reversal was correct; the actual lever here is regularization/class
balance, not vocabulary pruning.

**Still not "fixed" in any strong sense**: 67.5% is only moderately better than a coin flip. The
architecture is capped by the available training data being either narrow-domain (690 sitcom lines)
or a different register (headlines) from everyday typed sentences. If asked "how would you actually
get this much higher," the honest answer is **more conversational-register labeled sarcasm data**
(e.g. Reddit SARC, Twitter/iSarcasm corpora) — not further tuning of the same TF-IDF + LogReg pipeline
on the same two data sources.

**Voice — root cause found: flat prosody collapses the prediction, and the safety net doesn't always catch it.**
Generated synthetic TTS audio (macOS `say`, multiple voices) reading both a sarcastic-worded and a
sincere-worded sentence and sent both through `/api/analyze/audio`. **Both** came back
"Non-Sarcastic" at 65-70% confidence — the text content was irrelevant to the result. **Diagnosis**:
the Random Forest learned sitcom-actor *delivery style* (exaggerated pitch/energy variation) as its
main sarcasm signal; flat, non-theatrical prosody (which TTS — and plausibly a calm person speaking
into a laptop mic — produces) doesn't carry that signal, so the model falls back toward whichever
class has flatter average prosody in the 690-clip training set, regardless of what's actually said.

**The existing domain-shift guard (`MlService._typicality()`, threshold `mean_z_score > 1.5`) missed
most of this**: 3 of 4 synthetic test clips scored 1.08-1.16, under the threshold, so no warning was
shown even though the prediction was driven by acoustic mismatch rather than real signal. This was
**not** "fixed" by lowering the threshold — 4 synthetic samples is too small a basis to recalibrate a
safety check confidently, and TTS has its own unnatural acoustic fingerprint that may not represent a
real person's mic recording anyway. The honest, stated path forward is collecting a real
(non-synthetic) out-of-domain audio sample set to calibrate the threshold properly, and/or audio data
augmentation (pitch-shift, time-stretch, noise injection, simulated room/mic responses) on the
existing 690 clips to make the Random Forest less dependent on one narrow acoustic "fingerprint" —
not something that could be validated in this session without new labeled data.

**Takeaway worth stating explicitly in a viva**: "can it be fixed" has a real but bounded answer —
one genuine, measured improvement was found and shipped for text (class-balanced regularization), and
one specific, confirmed failure mode was found for voice (flat-prosody collapse, under-caught by the
existing guard) with a concrete next step (more/better-targeted training and calibration data) rather
than a quick code fix. Both diagnoses came from inspecting the model's own explanation output
(`_top_terms`, `domain_shift`) on fresh test inputs — not from re-reading the code, and not from the
project's own pre-existing metrics, which were structurally blind to both issues.
