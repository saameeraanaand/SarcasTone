# SarcasTone — CLAUDE.md

Guidance for Claude Code (or any agent) working in this repo.

## What this is

A B.Tech CSE research project comparing **text-only**, **speech-only**, and **multimodal**
(late fusion of the two) sarcasm classifiers on the **MUStARD** dataset (690 sitcom utterances,
Castro et al., ACL 2019). A FastAPI backend serves predictions from scikit-learn models; a
React dashboard visualizes everything. The project's core principle, stated in the README:
**every number shown in the UI is read from `results/metrics.json`, produced by the training
script — nothing is hardcoded.** Preserve that invariant in any change.

## Architecture

```
backend/app/
  main.py          FastAPI app — ALL routes live here directly (routes/, schemas/, services/
                    __init__.py files are empty placeholders; don't be misled by their names)
  schemas/api.py    Pydantic request/response models
  services/ml_service.py   Loads joblib models + results/metrics.json, runs inference
  ml/data.py        Loads dataset/sarcasm_data.json -> DataFrame, text cleaning
  ml/features.py    Librosa prosody feature extraction (pitch, MFCC, energy, pauses, rate)
  ml/train.py       Trains + 5-fold GroupKFold-by-speaker evaluates all 3 models,
                    writes results/metrics.json and backend/app/models/*.joblib
  models/*.joblib   Trained pipelines (text_model.joblib is committed; speech/fusion are not,
                    since they require audio that isn't in the repo)

frontend/src/
  pages/            Landing, Studio (live analysis), Speech, Models, Dataset, Research
  services/api.ts   Typed fetch wrapper for every backend endpoint
  components/       Navbar, Toast, Waveform, AnalysisContext, ui primitives
  charts/           Recharts wrappers for audio/metrics visualizations

dataset/sarcasm_data.json   MUStARD transcripts/labels (committed)
dataset/audio/              WAV clips — NOT in git, generated by scripts/setup_audio.py
results/metrics.json        Written by `python -m app.ml.train`; the single source of truth
                             the whole frontend renders from
results/exploratory_text.json  Ablations from experiments/exploratory_text_variants.py
experiments/                 Exploratory/ablation scripts, not part of the official pipeline
scripts/setup_audio.py       One-shot: download MUStARD raw clips, extract WAVs, train all 3 models
```

## Current state (as of this session)

- Backend installs and runs cleanly (Python 3.14, FastAPI, scikit-learn, librosa, numba all compatible).
- Frontend installs, type-checks, and builds cleanly (`npm run build`).
- Verified end-to-end in a browser: Studio page text analysis round-trips through
  `/api/analyze/text` and renders real model output.
- All three models are trained. Speech-only: 62.3% acc / F1 0.596 / ROC-AUC 0.676. Multimodal
  (late fusion, see below): 62.0% acc / F1 0.593 / ROC-AUC 0.677. Text-only's official MUStARD
  speaker-independent metric is 49.0% acc / F1 0.351 / ROC-AUC 0.446 — near chance by design on
  this narrow metric (see README "Interpretation"), but the *deployed* text model is trained on
  MUStARD + ~28.6k generic English headlines and scores 84.3% acc / F1 0.838 / ROC-AUC 0.924 on a
  held-out 4,293-example generic-English check (`text_only_generic_english_holdout` in
  `results/metrics.json`) — see "Text model generalization" below for why both numbers exist and
  which one to trust for judging real-world quality. Multimodal is late fusion built on top of
  that improved text model, not a separate joint model — see "Multimodal is late fusion" below.
  `dataset/audio/` (690 WAVs, ~111MB, gitignored) was populated via
  `scripts/setup_audio.py`, which downloads MUStARD's raw clips from Hugging Face, extracts
  audio with ffmpeg, and retrains all three models. The raw zip and extracted video clips are
  deleted after extraction — only the WAVs are kept.
- `backend/app/models/{speech,fusion}_model.joblib` are **not committed to git** (gitignored,
  since the audio they're trained on isn't in the repo either). Only `text_model.joblib` ships
  in the repo. Anyone cloning fresh gets text-only until they run `scripts/setup_audio.py`.
  The backend/UI already handle a missing speech/fusion model gracefully (health check's
  `audio_models_trained` flag, "not trained" states on the Models/Speech pages) — preserve
  that path, don't assume all three models always exist on disk.

## Running it

```bash
# Backend
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --port 8000 --reload

# Frontend
cd frontend
npm install
npm run dev   # http://localhost:5173, proxies /api -> http://127.0.0.1:8000
```

Or just `./run_backend.sh` and `./run_frontend.sh` from the repo root.

**Port note:** `vite.config.ts` hardcodes the dev proxy to `http://127.0.0.1:8000`, and
`run_backend.sh` runs uvicorn on 8000 too. On a machine where something else already owns
port 8000 (checked with `lsof -i :8000`), run the backend on a free port and point
`frontend/vite.config.ts`'s `server.proxy["/api"]` at it instead — don't just assume 8000 is free.

## Conventions worth preserving

- **No hardcoded metrics.** Every number in the UI must trace back to `results/metrics.json`
  (model metrics), `results/exploratory_text.json` (ablations), or a live `/api/analyze/*` /
  `/api/dataset/*` call. If you add a model or metric, wire it through `train.py` ->
  `metrics.json` -> `MlService`/`main.py` -> `frontend/src/services/api.ts` -> the page —
  don't inline a number in a component.
- **Speaker-independent evaluation.** Training/eval uses `GroupKFold` grouped by `speaker`
  specifically to avoid vocabulary/speaker leakage (see README "Interpretation" — a random
  split inflates text-only accuracy to 59% vs. 48.8% speaker-independent). Don't swap this
  for a plain random split without calling it out as a different, less honest protocol.
- **Vectorizers/scalers fit inside each CV fold**, never on the full dataset before splitting —
  this is what makes the reported metrics leakage-free. Preserve this in any pipeline change.
- **Graceful missing-model handling.** `MlService` and the API only load models that exist on
  disk and report `model_available` accordingly; the frontend renders explicit "not trained"
  states rather than guessing. Keep this pattern when touching `ml_service.py` or the Models/
  Speech pages — never fabricate a prediction or metric when a model isn't trained.
- **Dense, compact backend style.** `main.py` and `ml_service.py` intentionally pack multiple
  statements per line and favor terse, direct FastAPI/pandas idioms over heavy abstraction.
  Match the existing style rather than expanding it into a more "enterprise" layout.
- Large dataset artifacts (`dataset/audio/`, `dataset/raw_clips/`, zips, `experiments/audio_features.csv`)
  are gitignored on purpose — never try to commit them.

## Live-mic audio: known limitation and what's been done about it

The speech/multimodal models are trained on only 690 TV-sitcom clips (studio-mixed audio, specific
actors). A live recording from a user's own mic has a very different acoustic "fingerprint" (loudness,
spectral balance, noise floor), and tree ensembles tend to fall back toward ~50/50 probabilities on
inputs far outside their training distribution — this was confirmed empirically (in-distribution MUStARD
clips: 68-92% confidence and correct; synthetic out-of-domain speech: confidence collapsed toward 50/50
regardless of content).

Mitigations in place (`backend/app/ml/features.py::load_audio`, `ml_service.py::_typicality`):
- Audio is high-pass filtered (removes DC offset/rumble that studio audio doesn't have) and
  RMS-normalized to a fixed target loudness before feature extraction — applied identically at train
  and serve time via the shared `load_audio()` function. This measurably improved confidence on
  out-of-domain test audio without hurting in-distribution CV accuracy.
- `frontend/src/hooks/useRecorder.ts` requests `autoGainControl`/`noiseSuppression`/mono from
  `getUserMedia`, so live recordings are cleaner and more level-consistent before they ever reach the
  backend.
- `MlService._typicality()` computes a z-score of the live feature vector against the trained
  StandardScaler's mean/std (reused from the fitted pipeline, not a separate stats store) and flags
  `domain_shift.out_of_distribution` when a recording looks statistically unlike the training set.
  `AudioResult.domain_shift` carries this to the frontend; `Results.tsx` renders a visible warning
  banner when it's true, so a near-50/50 result reads as "the model doesn't know" rather than a
  confidently-presented number.
- There is no code fix that makes a 690-sample, single-domain dataset truly generalize to arbitrary
  voices/environments — that needs more diverse training data. Don't over-promise accuracy on live
  recordings; the honest framing is "measured acoustic features are always real, the sarcasm
  prediction is weak evidence, weakest of all on audio unlike the training domain."
- If retraining after any `features.py` change: delete `experiments/audio_features.csv` first — it's
  an id-keyed feature cache that `build_audio_features()` reuses across runs, so a feature-extraction
  change silently has no effect unless the cache is cleared.

## Text model generalization

The original text model (TF-IDF+LogReg trained on MUStARD's 690 lines only) was confirmed, concretely,
to perform badly on ordinary English: wrong on most of a manual probe set of everyday sarcastic/sincere
sentences (not sitcom dialogue) — e.g. "Oh great, another meeting, just what I needed" predicted
Non-Sarcastic, "The weather is nice today" predicted Sarcastic. This is not a code bug (label mapping
and the frontend's probability display were both independently audited and verified correct against
20/20 ground-truth MUStARD samples) — it's a vocabulary/generalization problem: 690 lines from 4 TV
shows is too narrow a training set for generic conversational sarcasm.

**What's in place now** (`backend/app/ml/train.py`, `backend/app/ml/data.py`):
- `load_external_text()`: the text model is trained on MUStARD + `dataset/external/sarcasm_headlines.json`
  (~28.6k rows, News Headlines Sarcasm Dataset, Misra & Arora, CC0, downloaded from the public GitHub repo,
  gitignored — not in git). `evaluate()` takes optional `extra_X`/`extra_y` added to each fold's *training*
  split only; the held-out evaluation fold is always pure MUStARD, so the officially reported
  speaker-independent metric stays honest and uncontaminated.
- `sentiment_shift()` (in `data.py`, shared by train and serve): an explicit feature — VADER compound
  sentiment of the sentence's first half vs. second half — fed into the classifier via a `ColumnTransformer`
  alongside TF-IDF, specifically so "positive setup, negative payoff" sentences have a dedicated signal
  instead of relying on scattered word weights to happen to capture that structure.
- `external_holdout_eval()`: a large-N (~4,293 example) held-out generic-English check, reported as
  `text_only_generic_english_holdout` in `results/metrics.json`. **Use this, not a handful of manual
  examples, to judge whether a pipeline change to the text model actually helps.** A small manual probe
  (even 8 carefully chosen sentences) is noisy enough to flip between "6/8 correct" and "3/8 correct" from
  one unrelated change — not a reliable signal for this kind of decision.

**Lesson learned in this session, worth repeating:** stripping English stopwords (`stop_words="english"`)
looked like an improvement on one specific failing example (it removed a spurious high-weight token, "an",
at -1.01) but measured *worse* on the 4.3k-example holdout (80.8% vs. 84.3% accuracy, 0.89 vs. 0.924
ROC-AUC) — reverted. The sentiment-contrast feature, by contrast, is statistically a wash on the large
holdout (84.2% vs. 84.3%, within noise) but was kept anyway because it's not harmful, it directly targets
a demonstrated failure pattern, and it adds a transparent, labeled term to the explanation output. Don't
re-add stopword removal, and don't drop the sentiment-contrast feature, without re-running
`external_holdout_eval()` for both variants and comparing on that number.

Final numbers (see `results/metrics.json`): MUStARD held-out 49.0% acc / F1 0.351 / ROC-AUC 0.446 (near
chance, as before — this narrow sitcom-specific metric doesn't reflect the deployed model's real
usefulness). Generic-English holdout: 84.3% acc / F1 0.838 / ROC-AUC 0.924 — this is the number that
matters for judging real-world quality, though it still measures headline-style English specifically,
not spoken conversation, so don't present it as "84% on anything you type."

Speech-only was not similarly augmented — the headline dataset has no audio, and MUStARD is the only
source of labeled audio in this project. Its generalization gap (see "Live-mic audio" above) remains
open; loudness normalization narrowed it but didn't close it.

**Follow-up fix (this session): function-word overfitting on conversational input.** Inspecting
`MlService._top_terms()` on real typed sentences (not headlines) showed the LogReg routinely giving
function words like "the"/"is"/"my"/"he"/"his" bigger coefficients (up to ~1.5) than genuine sarcasm
cues or the dedicated `sentiment_shift` feature (~0.05) — the model had overfit to headline-register
quirks (e.g. article/pronoun usage patterns specific to news headlines) rather than sarcasm itself.
This was invisible to `text_only_generic_english_holdout` because that holdout is drawn from the same
headline register as training — it can reward exactly this kind of overfitting. Built a 40-sentence
hand-labeled conversational probe set (ordinary typed sentences, not headlines, never trained on) and
grid-searched `C` / `class_weight` in `text_pipe()` against it. **Changed `text_pipe()` to
`LogisticRegression(C=0.3, class_weight="balanced")`** (was `C=1.0`, no `class_weight`): conversational
probe accuracy 60%→67.5%, at a small cost to the headline holdout (84.3%→82.3% accuracy, 0.924→0.907
ROC-AUC) and no material change to the already-near-chance official MUStARD metric (0.490→0.474
accuracy). Re-tried `stop_words="english"` combined with this change too — still worse on both the
headline holdout *and* the conversational probe, confirming the earlier revert was right; the fix here
is regularization/class-balance, not stopword removal. **Still far from solved**: 67.5% is only
moderately better than chance on ordinary sentences — the architecture is capped by training data that
is either narrow-domain (690 MUStARD lines) or a different register (headlines) from everyday typed
text. The real next step for a meaningfully better number is training on genuinely conversational
sarcasm data (e.g. Reddit SARC, Twitter/iSarcasm corpora), not further hyperparameter tuning of this
same TF-IDF pipeline. **Lesson, worth repeating alongside the stopword one above:** a same-distribution
holdout (headlines-in, headlines-out) cannot detect overfitting to that distribution's own register —
any future pipeline change should also be checked against a held-out set in the *target* register
(ordinary conversational sentences), not just the headline holdout.

**Voice/live-mic failure mode confirmed empirically (this session):** fed the speech model synthetic
TTS audio (macOS `say`, multiple voices) of both sarcastic- and sincere-worded sentences. All of them
were predicted "Non-Sarcastic" with ~65-70% confidence regardless of the words spoken, because flat/
non-theatrical prosody (no exaggerated pitch/energy variation) doesn't carry the signal the Random
Forest learned from sitcom-actor delivery — it's effectively reading delivery style, not content, and
falls back toward whichever class has flatter prosody on average in the 690-clip training set.
**The existing out-of-distribution guard did not reliably catch this**: 3 of 4 synthetic test clips
scored `mean_z_score` 1.08-1.16, under the `_typicality()` threshold of 1.5, so no warning was shown
despite the prediction being driven by acoustic mismatch rather than real signal. Didn't change the
threshold based on only 4 synthetic samples (too small/noisy to calibrate confidently, and TTS audio
has its own unnatural acoustic signature that may not represent real human mic recordings well either)
— flagging this as an open item: before trusting or further tuning `_typicality()`'s threshold, collect
a real out-of-domain set (actual people on laptop mics, not TTS) large enough to calibrate it properly.

## Multimodal is late fusion, not joint feature fusion

Originally multimodal (`fusion_pipe()`, now removed) trained one `ColumnTransformer`-based model on raw
TF-IDF + prosody features together, fit only on MUStARD's 690 audio-labeled rows — headlines have no
audio, so they couldn't be mixed in. That meant multimodal kept the exact narrow-vocabulary problem the
text model had, even after the text model itself got the headline-augmentation fix: a user tested this
directly (typed a hard sentence + recorded their own voice) and got 91% confidence in the wrong direction.

Fix (`backend/app/ml/fusion.py`, `train.py::evaluate_fusion`): late fusion / stacking. `StackedFusion`
holds references to the already-trained `text_model` and `speech_model`, and a small 2-input
`LogisticRegression` meta-model that learns how to weight `predict_proba` from each. This lets the text
side keep its full headline-augmented training (so multimodal inherits that fix) while the prosody side
keeps its own dedicated Random Forest; only the lightweight meta-model is actually fit on the 690 rows
where both audio and text exist, so there's no serious overfitting risk from a 2-feature classifier.

`fusion_model.joblib` is now a pickled `StackedFusion` instance, not a plain sklearn `Pipeline` —
`MlService._audio_scaler()` and anything else reaching into its internals needs
`self.models["fusion"].speech_model.named_steps["sc"]`, not `.named_steps["fuse"].named_transformers_["a"]`
(the old joint-pipeline path, which no longer exists). `ml_service.py::audio()` for multimodal mode now
builds a DataFrame with `"clean"` + `SENT_COLS` + `FEATURE_NAMES` all present in one row (StackedFusion
slices out what each sub-model needs) rather than `"clean"` + raw prosody keys.

Measured result: multimodal's official MUStARD metric improved too (59.1%→62.0% accuracy, now on par
with speech-only instead of worse than it), and confidence on real in-distribution MUStARD audio+text
jumped to 92-97% (vs. ~70-85% with the old joint model). The specific adversarial sentence that prompted
this fix ("wonderful day, already had an accident" + a flat TTS recording) is *still* wrong (84.9% vs. the
old 91% — moved in the right direction, didn't flip) — don't claim this is "fixed" for every input; it's
a measured architectural improvement, not a guarantee on hard or adversarial sentences, especially ones
tested with synthetic TTS audio that carries none of the vocal delivery a real sarcastic human voice
would.
